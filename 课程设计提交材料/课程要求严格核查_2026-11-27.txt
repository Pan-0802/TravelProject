课程设计要求严格核查
核查日期：2026年11月27日
项目：个人旅行记录与智能规划系统（TravelProject）

一、结论与判定范围

严格结论：目前属于“部分满足”，不能按这份课件逐条判定为全部通过。
数据库和主要业务已有实质实现；但列表、表单反馈、界面状态、视觉规范，以及数据库初始化、Git 版本、报告举证、演示录屏等交付要求存在明确缺口。
“功能能使用”“测试通过”“报告已经生成”均不等于满足所有课程要求。不推算分数或通过率，因为课件未给出评分权重。

判定依据：老师提供的《9-2 数据库课程设计-最新--界面开发与工程规范.pptx》，共21页。以下页码采用文件中的实际幻灯片顺序。
核查对象：当前本地源码、SQL、Git 状态、现有提交材料、实际 MySQL 连接元数据、重新运行的构建与测试，以及对真实前端代码进行受控网络测试所得的界面证据。
本次只核查并新增本清单，没有为迎合结论修改业务源码、数据库结构、既有报告或既有录屏脚本。

状态含义：
【满足】当前实现及核查证据支持要求。
【部分满足】部分实现正确，但同一要求中仍有明确缺口。
【不满足】已有直接反例，或必交付物缺失。
【证据不足】尚无充分证据，不能当作通过，也不据此断言实现一定失败。

二、技术路线、页面结构及数据库设计

1. 技术路线可以自选（第21页）——【满足】
项目采用 Spring Boot + MyBatis + MySQL 与 Vue 3 + Element Plus。
课件中的 Python Web 示例不是唯一允许的语言；第21页明确允许自选路线。不能仅因采用 Java 而判不合格。

2. 三类页面、8～12个页面（第11页）——【基本满足】
当前有旅行等列表、旅行详情、创建/编辑表单，三类结构均存在。创建/编辑复用同一表单组件。
路由有9个业务页面、登录及注册页，共11个常规页面；另有404页面。按是否计入404，均未超过12页。
不足：景点、收藏主要采用卡片，未完全遵循课件所列“检索区＋表格＋分页”的统一列表结构；详情页关联数据已有体现，但写操作仍分散在多个列表行中。

3. 数据库设计文档基本内容（第19页）——【部分满足】
现有33页报告包含需求分析、概念设计、逻辑设计、物理设计、实现与验证等阶段，含 E-R 图、10张表的说明、核心代码及模块截图。
不能说“没有做数据库设计”；但有文档不代表后文所有举证要求均已满足。技术选型理由还可更明确解释为何采用当前架构；四态截图、六类缺陷自查、部署演练记录缺失，见后文。

三、列表页五条规范（第12页）

4. 检索区一行、表格上方、回车或按钮触发——【旅行列表满足；未据此证明全系统均满足】
旅行列表提供关键词、状态、查询与重置入口。本次核查未发现该页面检索区是主要障碍。

5. 列宽匹配、长文本截断并悬浮展示全文——【不满足】
旅行列表日期采用最小宽度而非固定宽度；80字旅行名称在受控测试中换行撑高至约84像素，没有省略号、title 或全文悬浮提示。
证据：frontend/src/views/trip/TripListView.vue；.course-build/course-audit/trip-long-text.png。

6. 数字与日期右对齐、文本左对齐——【不满足】
旅行列表日期、预算/支出列实际均为左对齐；消费列表金额、日期也未统一右对齐。
这是课件明文条目，不只是个人审美建议。

7. 右下角分页、每页20条、页码＋总数＋当前范围、翻页保留条件——【部分满足，整体未达标】
已做到：旅行列表分页放在右侧，有页码和总数；实测翻到第2页仍保留关键词。
未做到：旅行默认每页10条，收藏默认12条，消费默认10条；当前没有“第1～20条／共N条”这样的范围显示。
提供20条选项不能替代“默认每页20条”和“当前范围同时给出”的要求。
证据：TripListView.vue 默认 size:10；FavoriteView.vue 默认 size:12；ExpensePanel.vue 默认 size:10；ui-review-evidence.json。

8. 每行只保留查看，编辑/删除移入详情——【不满足】
旅行列表行同时有详情、编辑、删除；消费列表也有直接编辑、删除。
证据：TripListView.vue 操作列；ExpensePanel.vue 操作列；trip-normal.png。

四、表单、视觉及四种界面状态（第13～15页）

9. 前端、服务端、数据库三层校验——【主要链路满足】
前端必填规则实际生效；服务端有请求校验和业务校验；数据库有非空、唯一、检查约束及外键。
受控界面测试中，空旅行表单在名称、目的地、日期下方分别显示必填提示。
此项不表示穷举过所有字段的所有边界组合。

10. 错误紧跟对应字段，说明原因与修法——【部分满足】
前端必填校验已有字段下方提示。
服务端拒绝修改旅行日期时，只在顶部弹出“已有行程落在新日期范围外，请先调整子数据”；相应日期字段下没有提示。用户要自己定位错误。
受控422响应测试：字段错误提示数量为0，表单仍保留。需要把可定位的服务端错误映射到字段；非字段错误也应在表单内持续显示并给出下一步。
证据：trip-client-validation.png、trip-server-validation.png；TripFormDialog.vue。

11. 提交时禁用、防重复、成功通知——【基本满足】
受控慢保存测试中保存按钮确实禁用；成功消息与提交后的刷新已有实现。
但“新增跳详情”的状态要求尚未满足，见第17项。

12. 破坏性操作二次确认，明确对象与后果——【部分满足】
旅行删除确认正确：包含旅行名称，明确每日行程和消费一并删除且不可恢复。
消费删除有确认，但对象与不可恢复后果的文案未统一达到同等完整程度。不能把所有删除确认都判为没有做。

13. 灰阶为主、单一主色，颜色语义统一——【部分满足】
界面已有统一蓝色主色和常规错误、成功提示。系统还使用多种标签颜色，需按课件要求逐一统一其语义；本项未进行全页面逐像素验收，不以此单独断言所有页面失败。

14. 全系统只设三档字号、间距固定4/8/12/16/24——【不满足】
仅旅行列表一次实际渲染就出现12、13、14、22像素四种字号，已超出三档。
全局及页面样式存在10、14、18、20像素间距，以及2、6像素局部微调，未采用规定档位。
证据：frontend/src/styles/main.css；TripListView.vue；ui-review-evidence.json。

15. 加载态及超过3秒的响应标准——【部分满足；实际性能证据不足】
请求期间有 loading，保存也会禁用按钮。
受控4.5秒延迟测试在3.2秒时仍显示加载，没有超时状态；普通接口超时设置15秒，部分AI请求90秒。现状不能按课件“超过三秒无响应视为超时缺陷”直接判为全部合格。
这不是实测真实接口普遍要4.5秒，也不代表真实AI可以仅靠改超时值就做到3秒出完整结果。AI长任务需要明确的快速受理反馈、状态展示与重试/恢复方式，并在报告说明和验收具体口径；普通查询需实测响应。
证据：trip-loading-3200ms.png；request.ts、api/ai.ts、api/conversation.ts。

16. 空态、错误态准确且可恢复——【不满足】
已实现正常无数据提示和重置入口，但有两个可复现反例：
（1）旅行列表503失败后，顶部错误消息消失，表格变成“还没有旅行计划，点击新建旅行开始吧”。查询失败被呈现为没有数据，没有持续的错误区；刷新按钮虽在，但不能弥补状态混淆。
（2）收藏按关键词无匹配时仍提示“还没有收藏任何景点”，没有区分“没有收藏”与“筛选无结果”。
证据：trip-failure-after-toast.png、favorite-filter-empty.png；TripListView.vue 的 catch 清空数据逻辑。

17. 成功态：新增进入详情，修改返回列表并刷新——【部分满足】
有成功提示和列表刷新；但旅行新增与修改共用 handleSaved，只调用 loadTrips()，没有区分新增后跳详情。
第13页允许详情或列表，而第15页进一步明确新增跳详情；严格按较具体的状态要求判断，当前仍有缺口。
证据：frontend/src/views/trip/TripListView.vue 第189行开始的 handleSaved。

五、数据层四条强制要求（第17页）

18. SQL参数化——【业务查询满足；全仓库按字面规则仍有待整改项】
核查的业务查询使用 MyBatis #{...} 占位符，未发现把用户输入值直接拼进业务SQL的反例。
但 MysqlAcceptanceTest.java 第38、58行通过拼接系统生成的随机库名创建/清理隔离测试库。这不是用户输入注入漏洞，且有固定前缀与格式约束；数据库标识符也不能当普通值占位。
不过，老师写的是“代码中出现任何一处字符串拼接SQL即判缺陷”。按最严格的字面检查，此处不能隐藏，应改为预先准备的固定隔离库等实现，或在缺陷自查中说明标识符与参数值的边界。未经老师认可，不能把全仓库此项写成无条件全通过。

19. 多表操作事务、失败整体回滚——【已核查核心链路满足】
AI草稿写入正式旅行、每日活动创建/修改/排序、父旅行删除等核心多表写操作有事务及必要的父记录锁。
已有集成测试覆盖部分写入后失败回滚、日期范围、并发/幂等及归属限制。本次通过的是基础测试；MySQL专项27项没有运行，不等于在真实MySQL上全部重验通过。

20. 连接即用即关——【已核查实现满足】
业务访问由 MyBatis/Spring 管理连接与事务；直接 JDBC 检查使用 try-with-resources 释放 Connection、PreparedStatement、ResultSet。
使用连接池不等于漏关，正确释放后连接会归还连接池。没有进行长时间生产并发泄漏压测，不夸大为所有运行场景都已证明。

21. SQL层分页——【已核查主要列表满足】
旅行、景点、收藏、消费、AI记录及会话列表使用数据库 LIMIT/OFFSET；未发现把这些列表全表取出后在前端切片的实现。
一次旅行中的每日活动、受限的会话上下文等不是同一类全库列表，不能仅因读取集合就误判为分页违规。

六、六类缺陷自查（第18页）

22. SQL集中在数据访问模块——【部分满足】
主要SQL位于 Mapper，但 AiConversationService 中仍有表存在性探测SQL，ReadinessController 中也直接执行健康检查SQL。按“全部SQL集中”的字面要求，应统一抽到专门的数据访问层，并在自查表说明。

23. 真实凭据与历史——【已知凭据检查通过；不作绝对保证】
本地私密环境配置被忽略，.gitignore 已覆盖 .env、IDE配置、依赖与构建产物。
本次以当前实际使用的数据库密码、JWT密钥、高德和AI Key 在内存中比对197个未忽略文本文件及现有两次提交差异，未发现相同已知私密值。
没有在清单或日志中列出密钥。这不是对未知密钥、远程其他分支、外部截图或其他人电脑的完整泄露审计。演示账号口令属于测试数据，不应与私密API Key混为一谈。

24. 库、表、连接统一utf8mb4——【当前本机检查满足】
使用应用同款JDBC驱动与实际本地连接，只读查询到数据库、客户端和连接字符集均为utf8mb4；实际10张表均为utf8mb4排序规则。
不能仅因配置中写 characterEncoding=UTF-8 就判定连接只支持3字节；应以实际连接结果为依据。
证据：.course-build/course-audit/charset-evidence.txt。

25. 避免列表N+1，提供检索/排序索引——【已核查主要列表基本满足】
列表通过JOIN、聚合和已有查询结果返回关联信息，有主外键及相关索引；未发现旅行/收藏列表逐行再查询一次关联信息的主要反例。
未进行大数据量执行计划和负载基准，因此不将“有索引”写成“所有查询性能都已最优”。

26. 删除策略——【引用完整性已有处理；策略说明需补全】
项目采用物理删除，并通过外键 ON DELETE CASCADE / SET NULL 处理从属、可选引用；不能指控其一定会遗留孤儿记录。
课件允许物理删除时处理外键引用。项目应在文档列明哪些级联删除、哪些置空、哪些保留，以及用户确认的后果。没有统一软删除并不自动等于本项全部失败。

新增会话和消息表没有覆盖多轮聊天分支的种子数据。应区分“故意的失败样例”和“当前版本可成功保存的正常样例”。
